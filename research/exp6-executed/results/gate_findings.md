# Exp 6 finding: specs reject known-correct end states

Scope: gate only, 12 subset tasks. These states are not blind evaluation states. Branch `exp6-executed-specs`.
Per-root decisions: `gate_table.md` and `gate_decisions.json` (generated by `results_export.py`).
Counterfactual rule test: `rule_test.md` (generated by `rule_test.py`).

## Finding

On 21 known-correct end states from the 12 subset tasks, the spec executor accepts 7, rejects 11, and cannot decide 3 (UNDECIDED).

- Root level: 11 of 21 REJECT (52%). 14 of 21 are not accepted if UNDECIDED counts (67%).
- Task level: 6 of 12 tasks have at least one known-correct state that is not accepted. The other 6 accept every known-correct state.
- The 21 roots are not independent. Five REJECTs come from one predicate (f23acfd2 geometry). Two come from one table predicate (88fe4b2d).
- 17 of the 21 are OSWorld gold files. The official checker compares a gold file with itself, so its PASS on gold roots only shows the runner works. "Known-correct" here means the benchmark's reference answer, checked against the request.
- The Exp 5 figure (7.6%) is a different measure. It is the blind paired judge's rate of specs rated wrong (design doc, section 5). This gate measures how often an executed spec rejects a correct end state. The judge read specs, not executions, so this suggests the judge did not catch over-strict predicates. The two numbers do not measure the same thing, and this gate says nothing about how often specs accept wrong states on all 66 tasks.

## Rule test: "never pin order, names, geometry, or whitespace unless the request names them"

I applied each edit by hand to a copy of the spec's must list, then ran the same roots. The spec files are unchanged. This shows what the rule would change. It does not show what a spec writer would produce.

| cause (roots) | edit under the rule | result |
|---|---|---|
| order (42e0a640, 1273e544 gold1) | `sheet_names set_equal [...]` | Both accept. All mutants still REJECT. Prevented. |
| geometry (f23acfd2 gold2-4, positive) | drop the geometry predicate | All four accept. Mutants still REJECT. Prevented. |
| names (f23acfd2 gold1) | find the body shape by its text, not its name | Accepts once geometry is dropped. Mutants still REJECT. Prevented, but it needs rewritten predicates, not deletion. |
| whitespace (88fe4b2d gold3, gold4) | compare whitespace-normalized cell text | UNDECIDED, not ACCEPT. The prose clause still blocks acceptance. Partly prevented. |
| count and layout (936321ce gold2) | remove order and position pins, keep the count | Still REJECT. The 5x4 content check needs the whole block in one table. Not prevented. The rule does not name counts or layout. |
| contradiction (a9f325aa gold1) | not covered by the rule | Dropping predicate 2 gives ACCEPT. All five mutants still REJECT. Needs its own rule. |

Totals, with the prose clauses kept and all class-1 edits applied: REJECT 11 to 2, ACCEPT 7 to 14, UNDECIDED 3 to 5. The rule fully prevents 7 of the 11 REJECTs, partly prevents 2, and leaves 2 (the count/layout case and the contradiction).

Costs of the rule:

- Order and position pins were the only executable check of table placement in 936321ce. A new placement mutant (the table moved to the end of the document) was REJECT under the original spec. Under the rule it becomes UNDECIDED, because the prose clause is unparsed.
- Moving the prose clauses into footprint, to fix the class-3 UNDECIDEDs, is unsafe. Under that edit, the untouched 88fe4b2d start ACCEPTs, and so do the two sentence mutants (blank lines removed, one word changed). The spec's only check of the sentence split is that prose clause. Likewise, the placement mutant ACCEPTs.

## What a writing-time rule set would need

1. Never pin order, names, geometry, or whitespace unless the request names them. Tested above.
2. Never pin counts or layout (how many objects, how a block is split) unless the request names them. Not tested to a pass: the 936321ce variant still rejects, because the content check also needs cross-table row matching, which the grammar cannot express.
3. No predicate may pin a value that another predicate in the same spec allows to differ. This would have caught a9f325aa.
4. Do not move a stated requirement to prose. Each requirement the request states needs an executable predicate, and the grammar has to grow to cover it (sentence split, body order, cross-table rows).

## Numbers that still stand

- Mutants (40): the spec accepts 1 (57667013: nothing checks that other slides are unchanged). It leaves 2 UNDECIDED (88fe4b2d blank lines and word change). OSWorld's checker accepts 4 of the 37 runnable mutants (table and text edits it does not compare).
- Predicate parsing: 199 of 302 predicates across all 66 specs (65.9%) parse. 27 of 66 specs parse fully. An unparsed predicate makes a spec UNDECIDED.
- Gate-pass (accepts every known-correct root and rejects every mutant and start): 5 specs (6054afcb, 21760ecb, d53ff5ee, ecc2413d, 4d117223).

## Caveats

- 12 tasks, 21 roots, 40 mutants. Counts are small, and roots from one task are correlated. Cite the task-level counts first.
- The mutants and the rule edits are mine, not the spec writer's. The executor is also mine. Its decisions are its decisions.
- The rule test edits predicates by hand. It shows the effect of a rule, not the output of a model that follows it.
