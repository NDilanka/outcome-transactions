# Experiment 4a: Can OSWorld's outcome checkers be written as outcome specifications?

Date: 2026-10-28. Inputs: `research/OSWorld` (unmodified), `evaluation_examples/test_all.json` (368 tasks, 10 domains), the spec format in `docs/outcome-checking.md` section 4.2.
Outputs: `research/exp4a-checker-mapping.csv` (one row per checker function), `research/exp4a_aggregates.json` (computed numbers). Scripts: `research/exp4a_*.py` (`exp4a_mapping.py` holds the per-function judgments and computes everything below).

Task-weighted by function (each function weighted by its task count, 361 function-task pairs): yes 286 (79.2%), yes_with_new_reader 53 (14.7%), partial 22 (6.1%). This view treats `compare_table` and `check_include_exclude` as single judgments, so the strict task-level numbers above are the better figure.

Over all 368 tasks: 333 (90.5%) are expressible with the reader library below, 9 (2.4%) only partially, and 26 (7.1%) are not state checks at all.

**The most important qualification:** "expressible" means the check can be written in our format *if the spec author has what the OSWorld author had*. For **172 of 342 feasible tasks (50.3%)**, the checker compares against a hand-made gold artifact (a gold `.xlsx`, `.pptx`, `.docx`, image, PDF, etc.). Our format can express "result equals reference under projection P", but our spec is compiled from the request before any search, so it has no gold file. For those tasks the honest statement is: the *predicate* fits the format; the *expected value* would have to be produced some other way (rewritten as delta predicates against the before-state, or generated by the compiler). This experiment does not test whether that rewrite is possible.

(One function can have several kinds; task counts overlap.)

Operators the format needs beyond section 4.2's list, all observed:
- **Quantifiers and aggregates:** "every run in the last paragraph is struck", "every italic run is 14pt", "count of lines matching a time regex == 31", "every word is red iff it starts with a vowel".
- **Disjunction:** 28 tasks use `conj: "or"`, all as alternatives of the same function, mostly multiple acceptable gold files (12 are `compare_pptx_files`). `check_nfl_super_bowl_liv` also needs internal OR. Section 4.2 shows only a conjunctive list; `any_of` is required.
- **Graded scores:** 25 tasks return partial credit (mean fuzz ratio, difflib ratio, weighted field scores, test pass fraction). Our pass/fail format must pick a threshold, which changes semantics.
- **Reader-to-reader comparison:** window size == screen size; target paragraph indent == reference paragraph indent; image found by blob from the original deck.
- **App defaults in readers:** VLC checks treat a missing key as its default value (`qt-bgcone` defaults to `1`). A naive `config.key` reader would get these wrong.

## 4. Partial and not-expressible cases

Not expressible as a state predicate:
- `infeasible` (26 tasks, 7.1% of all tasks). Success means the agent declared the task impossible. There is no state to read. Our engine would need a separate "refuse" outcome, not a `must` predicate.

Partial (9 feasible tasks, 3 functions):
- `check_include_exclude`, 7 of its 20 tasks (`os/37887e8c`, `os/4d117223`, `os/5c1075ca`, `os/5ced85fc`, `os/6f56bf42`, `os/5812b315`, `multi_apps/b337d106`). The checker is "output contains SUCCESS" over a downloaded `eval.sh` or `check_password.sh`. The real logic is hidden in a shell script. It fits our format only through a `cmd.output` escape hatch, which defeats the purpose of typed readers. Rewriting each script as typed predicates is probably possible (the one I read checks file existence in three directories) but was not done here.
- `compare_references_gain` (1 task). The score is the normalized similarity gain toward gold relative to the original document, averaged per reference. Expressing it needs arithmetic over two similarity measures and graded output. The gold file stands in for "correct APA 7th style", which is really a judgment, so this is the one task flagged `fuzzy`.
- `compare_docx_paper_records` (1 task). It parses records from a document, aligns them to gold by fuzzy title match, then computes a weighted score over fields. Each piece fits the format, but the alignment plus weighting is a small program, not a predicate list.

## 5. Checks that need the original state

- **12 functions / 13 tasks (3.8%)** compare against the starting state explicitly: GIMP brightness, contrast, and saturation "increased or decreased vs original" plus structure similarity (4 tasks); resized, palette, mirrored, and green-background images vs the original (4); file-exists plus SSIM vs the original photo (1); stretching the original image in a deck (1); deduplicated train records as a subset of the original lines (1); reference-gain vs the original (1); slide background closer to target than to the original colour, with the original hard-coded as a literal (1). In OSWorld these get the "before" file by downloading a copy of the input. Our engine has it for free.
- **Footprint-style checks done through gold (19 tasks).** 13 `compare_table` tasks use `preserve_cells` ("existing reference cells must be unchanged"), and 6 Writer tasks run a full text-equality guard against gold before checking formatting ("you may only change formatting"). These are frame conditions written as gold comparisons. Our `footprint` section expresses them directly, without a gold file.
- More broadly, most of the 172 gold-artifact tasks have a gold file that equals the original plus the requested edit. Whole-file equality to gold is OSWorld's way of saying "this changed and nothing else did". This is the strongest case for 4.1 (check the difference): with the before-state, `result == gold` becomes `diff(original, result) == {intended delta}`. It also means the spec compiler must state the intended delta precisely, and this experiment does not show it can.

## 6. Patterns that suggest a much smaller library suffices

1. **A few checkers do most of the work.** `compare_table` (59 tasks) and `compare_pptx_files` (35) together cover 94 of 342 feasible tasks (27%). 78 of 120 functions are used by exactly one task, and 102 by three or fewer. Most of the 120 are one-off wrappers around the same handful of operators.
2. **About 7 operators cover nearly everything.** These are equality, contains/exclude, regex, numeric tolerance/range, set/list equality, similarity >= threshold, and quantifiers/count, plus `any_of`. "Reference compare" is equality between two readers under a projection, not a separate operator.
3. **Most readers are one shape:** parse a structured artifact into a tree and select a path. That covers `json.path`, `config.key`, `xlsx.*`, `docx.*`, `pptx.*`, `a11y.tree`, `html.dom`, and the browser prefs and bookmarks JSON. A generic "document model + selector" reader with per-format parsers could stand in for about 35 of the 57 readers. Parser quality is where the risk is: the `_robust` pptx variant exists only because LibreOffice saves theme colours that python-pptx misreads.
4. **Perceptual checks are a small, separate library.** SSIM, perceptual hash, MFCC, OCR, and colour family together cover about 25 tasks, concentrated in GIMP, VLC, and Impress media.
5. **Many single-purpose functions reduce to `config.key == literal`.** The seven VLC rc checks, the LibreOffice registry checks, and the GIMP sessionrc check are near-duplicates.

## 7. Other findings

- **The evaluator acts on the desktop before reading.** 200 of 342 feasible tasks have a `postconfig` that activates windows, presses Ctrl+S, closes apps, or runs commands before the checker reads files. OSWorld reads persisted files, so it must first force the app to save. Our readers would need to read the live document through the bridge, or the engine must flush state the same way. Either way, "read the state" is not side-effect-free in practice.
- **Some checks verify method, not outcome.** 4 tasks grep `~/.bash_history` or the process tree to confirm the agent used the terminal or a `--convert-to` command line. Our format can read the history file, but these are process constraints, not outcomes.
- **Some checks read state outside the machine.** 7 tasks read Google Drive. 11 compute the expected value at evaluation time from the clock or live websites, so the "same" spec can pass today and fail tomorrow.
- **Some checkers are weaker than their requests.** `has_page_numbers_in_footers` does not check "bottom left". `compare_subscript_contains` passes if any one run pair is subscript in both files. `check_textbox_on_leftside` only checks for any dark pixel in the left 35%. Vague words are codified as thresholds in about 11 tasks ("tone down", "vibrant", "blackish", "red"). OSWorld treats these as deterministic; a model writing our specs would face the same choice.
- **Similar-looking checkers use similar-looking predicates with different meanings.** For example, the brightness check passes when the original is brighter than the result. Any automated translation of OSWorld checkers into specs must read the argument order carefully.

## 8. Method and limitations

- One annotator (this agent) read every function. For the two 570-line functions (`compare_table`, `compare_pptx_files`) I read the rule dispatch and option list, not every helper. Judgments are recorded per function in `exp4a_mapping.py`. Per-task readers come from the task's getter types plus a regex classification of shell commands (`cmd_reader`), so a few tasks may be misclassified.
- The reader vocabulary is my normalization. A different grouping changes the count (57) but not the family-level picture.
- "Expressible" means a predicate in the 4.2 format, extended with quantifiers, `any_of`, thresholds for graded scores, and the named derived measures, could encode the same pass/fail decision. Nothing was executed. No spec was written for any task and run against OSWorld outcomes. Fidelity, especially for gold-based and similarity-based checks, is untested.
- Task counts use `test_all.json` (368 tasks). Multi-function tasks take their worst function's status. `compare_table` tasks are split by their rule types: tasks with chart or pivot rules count as `yes_with_new_reader`.
- The `fuzzy` flag is conservative: only one task's checker substitutes for a judgment that code cannot make. If vague-term thresholds count as fuzzy, about 11 more tasks qualify.
- This measures whether OSWorld's *checkers* are expressible. It does not measure whether OSWorld's checkers are *correct*, and it does not show that our compiler can produce such specs from the request alone. Section 1's gold-artifact caveat is the main open question.
